# Known Bugs / Live Testing Findings

Tracked during manual live testing (Phase 7 CLI). Not spec — a running log to fix later.

## 1. `windower targets` lists many phantom "Desktop" window entries

**Found:** Phase 7 live test, macOS sidecar, `windower targets --json`.

**Symptom:** Output includes dozens of `kind: "window"` entries with `title: "Desktop"`, empty `appName`/`appBundleId`, and `bounds` matching a full external-display resolution (e.g. `7680x2160`) — far more than the number of real on-screen windows. Likely one phantom entry per virtual desktop/Space (or per display arrangement) rather than actual user windows.

**Impact:** Noisy `targets` output; agents/users must filter these out manually to find real windows. Not currently blocking (real windows still resolve correctly), but hurts target discovery UX.

**Suspected source:** `native/macos` window enumeration (Phase 2, `CGWindowListCopyWindowInfo` or similar) likely picking up desktop/wallpaper layer windows per Space that aren't real app windows.

**Fix:** `native/macos/Sources/WindowerSidecarCore/Enumeration.swift` `mapWindow` now also skips windows whose `owningApplication` has an empty `applicationName` or `bundleIdentifier` — the phantom entries had a title but no real app identity. Real Finder desktop window (one instance, `appName: "Finder"`) still surfaces correctly.

**Verified:** live-tested with `windower targets --json` after `swift build` — window count on this machine dropped from ~65 (many empty-app "Desktop" duplicates) to 27 real windows, all with non-empty `appName`. `swift test` — 100/100 pass.

**Status:** Closed.

## 2. Narration mux failures are silently swallowed with no logging

**Found:** Phase 11 live test, real macOS sidecar recording + real `say`-generated AIFF narration muxed via `stop_recording({ narration })`.

**Symptom:** On the first live-test attempt, `stop_recording` returned a normal-looking success result: `outputPath`, `manifestPath`, and a full `manifest`. But `manifest.narration` was completely absent (both in the RPC result and in `manifest.json` on disk), and `ffmpeg -i <outputPath>` showed only the original video stream — no narration audio track had been muxed in at all. No error was thrown or surfaced anywhere in the MCP tool result.

**Root cause (this occurrence):** environmental, not a logic bug in `narration-mux.ts` itself — the long-lived daemon process had been started ~11 minutes *before* `apps/daemon/dist/session-manager.js`/`narration-mux.js` were rebuilt with the narration feature, so it was serving stale in-memory code. Killing the stale daemon (and the two stale MCP-server stdio processes whose memoized `DaemonClient` connections died with it) and letting them respawn against the current build fixed it; a clean rerun produced a correct mux (1 video + 1 AAC audio stream, video untouched, `manifest.narration` present with `trackIndex`).

**Real gap exposed:** `apps/daemon/src/session-manager.ts` (`stopRecording`, ~lines 281-300) deliberately swallows any `muxNarration` failure with an empty `catch {}` so a mux problem doesn't fail an otherwise-good recording — that's a reasonable product choice, documented in `narration-mux.ts`'s file-header comment. But nothing is logged when it happens. Any future mux failure (bad ffmpeg-static binary, disk full, permissions, a real regression) will look identical to "narration wasn't requested" from the caller's point of view — a video with no narration and no `manifest.narration`, no diagnostic. Same pattern also applies to the adjacent `EventTimelineWriter.finalize()` swallow a few lines above.

**Suggested fix:** log the caught error (daemon's logger, whatever that is) before continuing, in both swallow sites, so silent failures are at least debuggable. Not yet fixed — not addressed by this test.

**Status:** Fixed. `apps/daemon/src/session-manager.ts`'s `stopRecording` now logs both swallowed errors via `console.error` (the only logging convention present in `apps/daemon`, matching `bin.ts`) before continuing: `[SessionManager] event timeline finalize failed for session <id>: <error>` and `[SessionManager] narration mux failed for session <id>: <error>`. Swallow-and-continue behavior is unchanged; only logging was added.

## 3. MCP server's memoized `DaemonClient` doesn't self-heal after the daemon dies mid-session

**Found:** Same Phase 11 live test, while investigating bug #2 above — after killing the stale daemon process to force a fresh respawn.

**Symptom:** Once the daemon process was killed, the next `mcp__windower__*` tool call failed with `[DAEMON_UNREACHABLE] DaemonClient is disposed`, and every subsequent call kept failing the same way — it never recovered on its own.

**Root cause:** `packages/mcp-server/src/daemon-client.ts`'s `getDaemonClient()` memoizes one `DaemonClient` promise for the process's whole lifetime, and only clears that memoized promise (`clientPromise = undefined`) in the `.catch()` of the *initial connect* — i.e. if `ensureDaemonRunning()` itself rejects. It has no path to recover once a previously-successful connection later gets disposed (e.g. the underlying daemon process dies): the disposed client just keeps getting returned and erroring forever, for the life of the MCP server process.

**Impact:** Any daemon crash/restart while an MCP server (Claude Code plugin, dev server, etc.) is connected permanently breaks that MCP server's ability to reach the daemon until the MCP server process itself is restarted. In this test, restarting the MCP server process (killing `packages/mcp-server/dist/index.js`) let the host respawn it and reconnect cleanly — no code fix required to work around it, but nothing in the code does this automatically.

**Suggested fix:** in `getDaemonClient()`, detect a disposed/unreachable client at call time (or catch `DAEMON_UNREACHABLE`-style errors from `client.call`) and clear `clientPromise` so the next call reconnects, mirroring the existing initial-connect retry behavior.

**Status:** Fixed. `DaemonClient` (`packages/core/src/daemon/client.ts`) now exposes a public `isDisposed` getter over its existing private `disposed` flag. `packages/mcp-server/src/daemon-client.ts`'s `getDaemonClient()` checks `isDisposed` on the resolved client; if the memoized connection has died, it drops `clientPromise` and reconnects (recursively, so the same call transparently gets a fresh client instead of only healing on the *next* call). Covered by a new test in `packages/mcp-server/src/daemon-client.test.ts`.

## 4. `startCapture` against a `window`-kind target crashes the sidecar (`CGS_REQUIRE_INIT` assertion)

**Found:** Phase 18 live test, macOS sidecar, dogfood-recording the windower-site marketing demo via `start_recording` targeting a real Chrome window (`{kind: "window", id: "138", ...}` from `list_targets`).

**Symptom:** `start_recording` (and the daemon's underlying `startCapture` call) fails immediately with `[INTERNAL_ERROR] Sidecar stream closed` — no structured `SidecarError`, just the transport dying. Reproduced directly against the compiled sidecar binary outside the daemon (feeding raw JSON-RPC over stdio): the process aborts with `Assertion failed: (did_initialize), function CGS_REQUIRE_INIT, file CGInitialization.c, line 44.` immediately after accepting a `startCapture` call whose `target.kind === "window"`.

**Isolation:** the exact same `startCapture` params, only with `target.kind` changed to `"display"` or `"region"` (same underlying display, region bounds matching the window's on-screen position), succeed cleanly — `{"result":{"started":true}}`. The crash is specific to the window-capture code path, not capture in general.

**Impact:** `capture.window` (a capability the sidecar advertises in `describe`) is completely broken — any caller (CLI `--kind window`, MCP `start_recording` with a window target, the Claude Code skill's normal target-selection flow) crashes the whole sidecar process instead of recording. Workaround used for Phase 18: record a `region` target with bounds matching the window's position/size instead of the window itself (loses automatic tracking if the window later moves, but captures the same pixels).

**Suspected source:** `native/macos/Sources/WindowerSidecarCore/CaptureService.swift`'s window-target branch of `SCContentFilter`/`SCStreamConfiguration` resolution (Phase 4) — something in that path touches a Core Graphics / window-server API that requires an initialized `CGS` connection this process doesn't have (plausibly an `AXUIElement`-adjacent or `CGWindowListCreateImage`-style call used only for window (not display/region) targets), and the resulting assertion aborts the whole process instead of throwing a catchable Swift error.

**Fix:** `native/macos/Sources/WindowerSidecarCore/CaptureService.swift`'s `startCapture(params:)` `"window"` case (~line 428) no longer calls `SCContentFilter(desktopIndependentWindow:)` — that initializer is confirmed to require a CGS/WindowServer session this headless stdio process never establishes, and was the sole source of the crash. It now resolves the `SCDisplay` the target window is on (new `resolveWindowDisplay(_:in:)` helper, ~line 801: matches by point-containment of the window's origin against `content.displays`, falls back to frame intersection, then to the first enumerated display, never throws unless there are zero displays) and builds the filter via `SCContentFilter(display:including:)` — the same initializer the `"display"`/`"region"` branches already use safely — restricted to just the target window. The capture is then cropped to the window's bounds using the same `sourceRect`/`destinationRect` pattern the `"region"` branch already uses (`CaptureConfigService.regionSourceRect`, converting the window's pixel bounds to display-relative points). `nativeWidth`/`nativeHeight` computation is unchanged. A comment at the call site documents why `desktopIndependentWindow` isn't used, so it isn't reintroduced without fixing the underlying CGS-init problem first. Known trade-off (documented in the same comment): unlike `desktopIndependentWindow`, capture no longer automatically follows the window if it's moved to another Space mid-recording.

**Verified:**
- `swift build` — clean.
- `swift test` — 118/118 pass (same count as before the fix).
- Direct binary test: fed raw JSON-RPC `startCapture`/`stopCapture` over stdio to the compiled `native/macos/.build/debug/windower-sidecar-macos` targeting a real on-screen window (`id: "138"`, Chrome, obtained via the sidecar's own `enumerateTargets`). No crash/assertion (confirmed both via a bare `startCapture`-only call against an off-Space window, which now returns a catchable `CAPTURE_FAILED` JSON-RPC error instead of aborting the process, and via a full start/stop pass against an on-screen window). `startCapture` returned `{"started":true}`, `stopCapture` returned a normal result, and the written file (`ffprobe`'d via the repo's vendored `ffprobe-static` darwin/arm64 binary) was a valid non-empty H.264 mp4 at the window's exact pixel bounds (3024x1718).
- Full MCP/daemon/sidecar path: killed the stale daemon process so the MCP server would respawn it against the freshly built sidecar, then called `mcp__windower__start_recording` with a real `{kind: "window", id: "138", ...}` target from `list_targets`, waited a few seconds, then `mcp__windower__stop_recording`. No `[INTERNAL_ERROR] Sidecar stream closed`; `stop_recording` returned a finalized `outputPath`/`manifestPath`/`manifest`, and the finalized mp4 (`ffprobe`'d) was a valid ~10.3s H.264 video at 3024x1718.

**Status:** Fixed.

## 5. Terminal-footage recording: `manifest.durationMs` doesn't match actual decodable video length

**Found:** Phase 18 live test, recording a region matching a terminal window while running real `windower` CLI commands.

**Symptom:** `stop_recording`'s manifest reported `video.durationMs: 17213.49` (~17.2s) for session `cbaf26ca-2cc1-4301-b9a8-254e3ddc277f`, but `ffprobe`/a full decode pass of the resulting mp4 (`4-2026-08-09T14-18-17.mp4`) showed only ~7.7-7.9s of actual decodable frames (138 frames at the recorded fps) — under half the claimed duration.

**Impact:** Any caller trusting `manifest.video.durationMs` (trim/post-processing tooling, UI duration displays, Phase 15's future auto-zoom/trim work) will be wrong by a large margin for at least some recordings — the file itself is shorter than claimed, not the other way around, so trimming logic that assumes the manifest duration is authoritative could seek past the end of real content.

**Suspected source:** Not investigated — could be `VideoAssetWriter`/`AVAssetWriter` finalization on the Swift side reporting a stale/wall-clock session duration instead of actual muxed-frame duration, or frames being dropped/not delivered to the writer for a long stretch without that being reflected in what's reported to the daemon at `stopCapture` time. Same category of bug as #6 below (frames not actually landing despite the capture session reporting healthy) — may share a root cause, worth investigating together.

**Fix:** Root cause confirmed: `native/macos/Sources/WindowerSidecarCore/CaptureService.swift`'s `stopCapture` computed `actualDurationMs` purely from wall-clock elapsed time (`Date().timeIntervalSince(context.startedAt) * 1000`), with no relation to how much content actually landed in the file — `VideoAssetWriter` never tracked frame timestamps or asset duration. Fixed in `native/macos/Sources/WindowerSidecarCore/VideoAssetWriter.swift`: `finish(completion:)` (line ~179) now, after `AVAssetWriter.finishWriting` reports `.completed`, loads the finished file via `AVURLAsset(url: outputURL).load(.duration)` (bridged into the existing completion-handler API via `Task { }`) and hands the real duration back to the caller in milliseconds through a new `Self.milliseconds(from:)` pure conversion helper (`CMTime` → `Double?`, `nil` for a non-numeric time). The completion signature changed from `Result<Void, Error>` to `Result<Double?, Error>` — `nil` on success means the write succeeded but the duration couldn't be read (corrupt/empty asset), which the caller treats as a fallback case, not a hard failure. `native/macos/Sources/WindowerSidecarCore/CaptureService.swift`'s `stopCapture` (line ~729) now keeps the wall-clock computation as `wallClockDurationMs` (diagnostic/fallback only, never reported directly) and uses `realDurationMs ?? wallClockDurationMs` as `actualDurationMs` in the RPC response — so a corrupt/unreadable asset still degrades gracefully to the old behavior instead of crashing. `Tests/windower-sidecar-macosTests/AudioAssetWriterTests.swift` and `VideoAssetWriterTests.swift` updated for the new `finish` signature.

**Verified:**
- `swift build` — clean.
- `swift test` — 122/122 pass (118 baseline + 4 new unit tests for `VideoAssetWriter.milliseconds(from:)` covering a numeric `CMTime`, `.indefinite`, `.invalid`, and `.zero`).
- Full MCP/daemon/sidecar path: killed the stale daemon (`apps/daemon/dist/bin.js`) so the MCP server would respawn one against the freshly built sidecar, called `mcp__windower__start_recording` against the `Built-in Retina Display` display target, waited ~6s, then `mcp__windower__stop_recording`. Manifest reported `video.durationMs: 11875`. `ffprobe` (`node_modules/.pnpm/ffprobe-static@3.1.0/.../ffprobe`) on the finalized mp4 (`Built-in Retina Display-2026-08-09T15-52-21.mp4`) reported `duration=11.875000` — an exact match to the millisecond, confirming `manifest.video.durationMs` is now asset-derived (same source `ffprobe` reads) rather than wall-clock. (This normal, no-frame-drop recording doesn't reproduce the original ~17.2s-vs-~7.8s divergence, but the exact match to `ffprobe` — rather than a wall-clock number that would only coincidentally agree to 3 decimal places — demonstrates the fix is reading the real asset duration.)

**Status:** Fixed.

## 6. Region/display capture can freeze on stale pixels for long stretches despite real on-screen activity

**Found:** Phase 18 live test, recording a `region` target matching a Chrome browser window while driving real scroll interactions via browser automation (`mcp__claude-in-chrome__computer` scroll actions) during the recording.

**Symptom:** First attempt: performed 3 distinct scroll actions with 1s waits between them during a ~26s recording, confirmed via live screenshots (accurate, DOM/CDP-based) that the page visibly progressed through 3+ different sections throughout. But the resulting video, when sampled frame-by-frame after the fact, showed the page sitting essentially motionless on one section for ~26 of the ~26s, with all real content changes compressed into the last ~1-2s. The recorded pixels did not track the actual on-screen/DOM state in real time — bumping the wait time between actions to 2-3s (three later attempts) fixed it, suggesting the screen-capture pipeline (or the window compositor) needs longer to "catch up" after an interaction than the interaction itself takes.

**Impact:** Recordings of fast-changing/interactive content can silently capture long stretches of stale/frozen frames even though the underlying app state changed correctly and promptly — the video is not a faithful record of what happened on screen, timing-wise. This is a serious correctness concern for the whole product ("Windower captures the session"), not just a Phase 18 inconvenience: any real demo with quick back-to-back interactions (not artificially spaced out by 2-3s waits) risks looking static in the output even though the actions happened.

**Suspected source:** Not investigated — could be `SCStream` frame delivery/backpressure in `CaptureService.swift` (Phase 4), GPU-compositor throttling of an occluded/backgrounded window that ScreenCaptureKit is reading from, or something specific to capturing a window/region that isn't the frontmost-and-focused surface at every instant. Notably: this was observed even when the target window *was* frontmost/focused per `list_targets`' `isFocused` field at capture start.

Worked around empirically by spacing interactions 2-3s apart during recording. Needs real investigation into `SCStream` frame-delivery timing under Phase 13's e2e/soak-test umbrella — this is exactly the kind of bug a 10+ minute soak test or a frame-timestamp-vs-wall-clock assertion would have caught.

**Diagnostics added (this session):** A follow-up pass found that `native/macos/Sources/WindowerSidecarCore/VideoAssetWriter.swift`'s `append(sampleBuffer:)` silently dropped any frame when `AVAssetWriterInput.isReadyForMoreMediaData` was `false` (or `input.append` itself returned `false`), with zero counting/logging — `CaptureService.swift`'s `CaptureStreamOutput.stream(_:didOutputSampleBuffer:of:)` discarded the return value entirely. There was no way to distinguish "SCK/WindowServer delivered stale/delayed frames" (upstream, outside this codebase) from "our own writer silently ate frames it was handed" (a real, in-our-control gap) — this is the actionable half of the bug, since region/display capture uses a full-display `SCContentFilter` with `sourceRect`/`destinationRect` cropping rather than a window-restricted filter, so `SCStreamConfiguration` tuning alone can't confirm or rule out the root cause. Added: (1) a `droppedFrameCount` counter on `VideoAssetWriter` and `AudioWriterInputHandle`, incremented on every `false` return from `append`; (2) PTS-gap ("stall") detection — `VideoAssetWriter` tracks the presentation timestamp of the last successfully-appended frame and, on each accepted frame, computes the gap since it; a gap exceeding `max(3x the configured frame interval, 500ms)` (`VideoAssetWriter.stallThresholdMs(forFps:)`) increments `stallEventCount` and updates `maxStallGapMs`; (3) `stopCapture` in `CaptureService.swift` now emits a `warn`-level `log` notification (existing notification type, unchanged wire shape — see `LogNotificationParams`) plus a direct stderr line summarizing both counters whenever either is nonzero, via `VideoAssetWriter.diagnosticsSummary()`. `StopCaptureResult`, the manifest schema, and `contracts/sidecar-protocol.md` are all unchanged — this is diagnostic-only instrumentation for the *next* time this reproduces, not a reported field.

**This does NOT confirm or rule out a root cause.** `swift build`/`swift test` (129/129, 122 baseline + 7 new unit tests covering `gapMilliseconds`/`stallThresholdMs`/stall-recording against synthetic `CMSampleBuffer`s) pass, and a real ~6s recording via the daemon/MCP path (killed the stale daemon first, confirmed `windower-sidecar-macos` respawned from the freshly built `native/macos/.build/debug` binary) completed cleanly with no crash and — as expected for a short, non-stressed recording — no drops/stalls, so no warn log fired. No attempt was made this session to force a genuine stall to see the new logging actually trigger.

**Live repro attempt (follow-up session):** Before repro'ing, traced where the new diagnostics actually surface end-to-end and found a real, separate gap: `apps/daemon/src/session-manager.ts` calls `this.spawnSidecar({ onExit, ... })` without an `onStderrLine` callback, and never subscribes to the sidecar's `"log"` notification (only `"event"` and `"captureEnded"` — grep confirmed no `.on("log"` anywhere in `apps/daemon/src`). `packages/core/src/process/sidecar-process.ts` does capture the sidecar's stderr line-by-line, but silently drops each line when `onStderrLine` is undefined. So as wired today, the bug #6 diagnostics (stderr line + `log` notification) are invisible through the normal CLI/MCP/daemon path — not fixed here since it's out of scope for this pass, but worth its own follow-up (wire `onStderrLine` to `console.error` and add a `client.on("log", ...)` handler in `session-manager.ts`, mirroring bug #2's fix).

Given that gap, repro'd by driving the compiled sidecar binary (`native/macos/.build/debug/windower-sidecar-macos`) directly over raw newline-delimited JSON-RPC on stdio (`describe` → `startCapture` → `stopCapture`), with stderr captured straight to a log file — bypassing the daemon so nothing could swallow the diagnostics. Four attempts:

1. **Region target, rapid CDP-driven scrolls (browser-extension automation), no explicit waits.** Video showed content completely unrelated to the page being scrolled — a YouTube video, then an unrelated coding-agent session, then a GitHub Actions page. Root cause: this machine's Chrome is a *single shared window* used concurrently by multiple other automated sessions on the same desktop (confirmed via `osascript` — one Chrome window, tabs including YouTube/GitHub Actions/ChatGPT/calendar alongside the target tab), and browser-extension automation drives tabs via CDP without necessarily bringing them to the real OS foreground. A `region` capture reads raw display compositor pixels, so it faithfully recorded whatever window/tab actually was frontmost — which wasn't the one being scripted. Not usable evidence either way for bug #6.
2. **Same region target, Chrome brought to real foreground via `osascript ... activate` first.** Better, but the video still showed unrelated content partway through (this machine also auto-switches active app during normal tool use, including this session's own Bash calls) — same shared-desktop contamination. Also not usable evidence for the region case.
3. **Window-kind target (`{kind:"window", id:"10979"}`) against a dedicated Chrome window created solely for this test**, driven with real OS-level keystrokes (`osascript`/System Events `key code 121`, not CDP) so the interaction is indistinguishable from a human at the keyboard. First pass fired 15 page-down/up/down presses back-to-back (<50ms apart) — video correctly showed the windower-site content (not contaminated, since window-kind capture reads the window's own surface via SCK regardless of on-screen occlusion/frontmost state) but all the motion landed in a single ~0.3s window, too fast to distinguish "correctly tracked" from "coarse sampling."
4. **Same window-kind setup, 10 page-down presses paced ~530ms apart** (faster cadence than the original bug's 1s-and-stalled case), with `eventTimeline` keystroke capture giving exact ground-truth timestamps (`t=4499,5043,5572,6096,6625,7163,7662,8153,8659,9201`ms into the session). Extracting frames every 0.5s and correlating against those timestamps: the video's visible scroll position advanced in lockstep, landing on each new section within ~0.5s (one sampling interval) of the corresponding real keystroke, reaching the bottom of the page by ~t=7.5–8s versus the last relevant keypress at ~t=7.7–8.2s. No multi-second lag, no content "compressed into the last 1–2s" pattern. `droppedFrameCount`/`stallEventCount` were 0 in every one of these four attempts (stderr empty, no warn `log` fired every time), including the two contaminated region attempts where the physical screen *did* undergo large, real, rapid content swaps.

**Conclusion:** Did not reproduce the original stale-pixels stall this session. For `window`-kind capture specifically, real rapid keyboard-driven interaction (faster cadence than the original failing case) tracked wall-clock state correctly with the new instrumentation reporting zero drops/stalls throughout — no evidence of either writer-side backpressure or SCK-side staleness under this test. The `region`-kind case (the one actually used in the original bug report) was not cleanly retested — this machine's desktop is shared by multiple concurrent automated sessions fighting over window focus, which makes `region` (raw display-compositor pixels) fundamentally unreliable to test here since any other session's window can occlude the target between frames; that occlusion-sensitivity is itself consistent with (but not proof of) the original hypothesis that region/display capture is more exposed to compositor-level effects than window capture. Next attempt should either use `window`-kind exclusively (given it appears immune to the desktop contamination and still exposes the same `VideoAssetWriter` pipeline), or be run on a non-shared machine/session so a `region` capture can be trusted to reflect only the intended interaction.

**Status:** Partially addressed, still not reproduced. Diagnostics are implemented and confirmed inert (correctly silent) when there is nothing to report, including under rapid, real, paced interaction against a `window`-kind capture — no writer-side drops/stalls occurred there. Root cause for the original `region`-kind stall remains unconfirmed; the diagnostics have never actually fired yet in any real recording. Separately, a real (if minor) gap was found and left unfixed: the daemon does not forward sidecar stderr or subscribe to `log` notifications, so as shipped these diagnostics are invisible through the normal CLI/MCP path — tracked as bug #7 below.

## 7. Daemon never surfaces the sidecar's `log` notifications or stderr — bug #6's diagnostics are invisible through the normal CLI/MCP path

**Found:** Same live-repro follow-up session as bug #6, while tracing where bug #6's new dropped-frame/stall diagnostics actually surface.

**Symptom:** `apps/daemon/src/session-manager.ts` spawns the sidecar via `this.spawnSidecar({ onExit, ... })` without an `onStderrLine` callback, and never subscribes to the sidecar's `"log"` notification anywhere (grep confirmed no `.on("log"` in `apps/daemon/src` — only `.on("event"` and `.on("captureEnded"` are wired). `packages/core/src/process/sidecar-process.ts` does capture the sidecar's stderr line-by-line, but silently discards each line whenever no `onStderrLine` callback was supplied.

**Impact:** Any `log` notification the sidecar emits (bug #6's new `warn`-level drop/stall summary, and the pre-existing keyboard-capture-unavailable warning from Phase 10's `EventTapCapture`/`main.swift`) is a dead letter through the normal `windower` CLI / MCP / Claude Code plugin path — none of it reaches a daemon log, a CLI `--json` output, or an MCP tool result. The only way to see this diagnostic output today is to bypass the daemon entirely and drive the compiled sidecar binary directly over raw JSON-RPC with stderr piped to a file by hand (as done to work around this exact gap during bug #6's live-repro attempt). This silently defeats the whole point of adding the bug #6 instrumentation for any real caller.

**Suspected fix:** mirror bug #2's fix pattern (`apps/daemon/src/session-manager.ts` already logs swallowed narration/event-timeline errors via `console.error`) — pass an `onStderrLine` callback into `spawnSidecar` that forwards each line to `console.error` (or whatever the daemon's established logging convention is), and add a `client.on("log", (params) => console.error(...))` handler alongside the existing `.on("event"`/`.on("captureEnded"` subscriptions in `session-manager.ts`, so `log` notifications are at minimum visible in the daemon's own process output. Not fixed yet.

**Fix:** `apps/daemon/src/session-manager.ts`'s `startRecording` (~line 204) now passes an `onStderrLine` callback into `spawnSidecar` that forwards each sidecar stderr line to `console.error` (`[SessionManager] sidecar[<id>] stderr: <line>`), and registers a `handle.client.on("log", ...)` handler alongside the existing `.on("event"` subscription (~line 241) that logs each `log` notification via `console.error` (`[SessionManager] sidecar[<id>] log (<level>): <message>`). Both bug #6's diagnostics (dropped-frame/stall warnings) and the pre-existing keyboard-capture-unavailable warning are now visible in the daemon's own process output through the normal CLI/MCP/daemon path — no daemon RPC/manifest shape changed.

**Verified:** `tsc --noEmit` (`apps/daemon`) — clean. `vitest run` (`apps/daemon`) — 62/62 pass, no regressions.

**Status:** Fixed.
