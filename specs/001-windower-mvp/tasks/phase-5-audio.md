## Phase 5 — Audio

**Goal:** Add system-audio and microphone capture as separate, correctly-synced tracks on top of Phase 4's video pipeline.

- ✅ System audio: `SCStreamConfiguration.capturesAudio = true`, route the audio sample buffers to a second `AVAssetWriterInput` (audio) alongside the video input in the same `AVAssetWriter`. (`CaptureSystemAudioOutput` in `CaptureService.swift`.)
- ✅ Microphone: `AVCaptureSession` + `AVCaptureDevice` (default or `AudioSettings.tracks[].deviceId`-selected) feeding a third `AVAssetWriterInput` when `separateTracks: true`, or mixed into the system-audio track when `false`. (`MicrophoneCaptureSource` wired into `CaptureSessionManager.startCapture`; `AudioTrackPlan.bothMixed` routes both sources into one shared `AudioWriterInputHandle` — see that case's doc comment for why this is an interleaving approximation, not true PCM-level mixing.)
- 🔵 Timestamp alignment: all inputs (video, system audio, mic) share the same `AVAssetWriter` session start time by construction (`VideoAssetWriter.addAudioInput` adds every audio input to the video input's writer, and only the video-driven `start(at:)` opens the session) — implemented, but the clap-test fixture verification itself (visual clap + audible clap, frame-accurate alignment measured in the actual output) requires a live Screen Recording + Microphone TCC grant and a GUI session this sandbox does not have; deferred to Phase 13's local e2e run, same limitation Phase 2-4 hit (CLAUDE.md "TCC permissions gate CI").
- ✅ Device enumeration for mic selection (`AVCaptureDevice.DiscoverySession`) — `AudioDeviceService.listMicrophoneDevices()`/`resolveDevice(deviceId:)` in `AudioCaptureConfig.swift`; not yet surfaced through `getPermissions` or a dedicated RPC method (Phase 7's `--mic-device` CLI flag is the consumer named in the phase goal, and Phase 7 hasn't started — wiring a listing endpoint before there's a caller was judged premature; the service function exists and is unit-tested, ready for Phase 7 to call).
- ✅ Graceful degradation: mic requested + `PermissionsService.microphoneStatus() == .denied` fails `startCapture` fast with `PERMISSION_DENIED`, before any writer/stream resource is created (`AudioPermissionGate.shouldFailFast`, unit tested in isolation per `CaptureServiceTests`).

**Exit criteria**

- 🔵 Matches `spec.md` acceptance item: system audio and mic record as separate, correctly-synced tracks. Implemented (see timestamp-alignment note above); NOT verified live — clap-test fixture verification needs Screen Recording + Microphone TCC grants and a GUI session, unavailable in this sandbox. Deferred to Phase 13.
- 🔵 `ffprobe` confirms track count/layout matches `AudioSettings` (2 tracks for system+mic separate, 1 for mixed). Not run — same TCC/GUI gap; the equivalent no-TCC-needed guarantee (`VideoAssetWriter.addAudioInput` unit tests plus this phase's `AudioTrackPlan`/writer-input-count wiring) is covered by Swift unit tests, but an actual `ffprobe`-verified output file is deferred to Phase 13.
- ✅ Denied mic permission with `audio-mic` requested produces a clear `PERMISSION_DENIED` error, not a silent no-audio recording — implemented and unit tested (`AudioPermissionGate`); the fail-fast happens before any `SCStream`/`AVCaptureSession` resource is created, so it does not require a real mic device or grant to verify.
