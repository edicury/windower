- **Phase 11 — Narration Hook** (2026-08-09): `stop_recording`/`windower stop`'s already-shipped `narration: { filePath, offsetMs }` param (schema/CLI/MCP wiring pre-existed from earlier phases) now actually does something — the daemon muxes the supplied audio file into the finished recording as an extra track.
  - **Mechanism decision: `ffmpeg` (via `ffmpeg-static`), not `AVFoundation`.** Muxing a finished video with a narration file isn't screen capture — it never touches ScreenCaptureKit/AX/AVFoundation capture APIs — so per `CLAUDE.md`'s "protocol before platform" rule it belongs in the OS-agnostic `apps/daemon`, not `native/macos`. `ffmpeg-static` (`^5.3.0`, added as a real dependency, lockfile updated) bundles a portable, statically-linked binary with no system-ffmpeg requirement and no network call at daemon runtime (the binary ships inside the npm package at `pnpm install` time — consistent with "no network calls anywhere in MVP", which is specifically about runtime behavior, not install-time package fetching that every dependency already does).
  - New `apps/daemon/src/narration-mux.ts`: `validateNarrationFile(filePath)` (stats the file, then runs `ffmpeg -i <file>` and greps stderr for an `Audio:` stream line — throws `DaemonError("INVALID_ARGS", ...)` on missing/non-audio input) and `muxNarration({videoPath, narrationFilePath, offsetMs, videoDurationMs})` (runs the mux, writes to `<video>.narration-tmp.mp4` next to the original, renames over it on success, deletes the temp file and rethrows on failure).
  - **Validation is fail-fast, before capture is stopped**: `session-manager.ts`'s `stopRecording` calls the injected `validateNarrationFile` immediately after confirming the session is `"recording"`, *before* `await this.store.save({..., state: "stopping"})` and before `handle.client.stopCapture(...)`. An invalid narration path throws immediately and the session is provably untouched — still `"recording"`, never transitions to `"stopping"`/`"finalized"` (covered by a session-manager test asserting `state` post-throw).
  - **Mux timing**: runs as a distinct post-step after `stopCapture` has already produced the finished video and after the manifest's video/audio/eventTimelinePath fields are assembled, immediately before `manifest.json` is written. `fileSize` for `file.sizeBytes` in the manifest is (necessarily) stat'd *after* the mux step, since a successful mux rewrites `outputPath` in place and changes its size — this required moving the pre-existing `stat(outputPath)` call later in the function, the one non-additive edit to existing control flow.
  - **Duration policy: truncate narration, never extend the video** — the mux command always applies `-t <videoDurationSec>` (from `stopCapture`'s `actualDurationMs`), so a narration file longer than the video is simply cut off at the video's end; the video's own duration is never extended to fit it. Chosen so "video duration" stays single-sourced from the sidecar's actual capture, not something narration mux could silently perturb.
  - **Offset policy: negative offsets clamp to 0** before building ffmpeg's `-itsoffset` arg (`clampOffsetMsToSeconds`, unit-tested directly) — there's no meaningful "before recording started" to place audio into. The manifest still records the caller's original, unclamped `offsetMs` (not the clamped value) so the request stays auditable. An offset at/beyond the video's duration isn't special-cased as an error; it degenerates into the truncate policy (0 audible seconds land in the output).
  - **Mux failure doesn't fail finalization**: `muxNarration` is called from `stopRecording` in a try/catch that swallows any error and simply leaves `manifest.narration` unset (schema already `.optional()`) — same swallow-and-continue style Phase 10 established for `EventTimelineWriter.finalize()` failures a few lines above. The base video and manifest are still written/saved either way. On success, `manifest.narration = { filePath, offsetMs (unclamped), trackIndex: session.audio.tracks.length }` (positions the muxed track after any pre-existing tracks).
  - Injectable via `SessionManagerOptions.validateNarrationFile`/`.muxNarration` (both optional, defaulting to the real `narration-mux.ts` implementations), following the exact precedent `spawnSidecar` already set in this file for test doubles — no real ffmpeg process needed to unit-test `session-manager.ts`'s narration branches.
  - TS-resolution gotcha, documented inline in `narration-mux.ts`: `ffmpeg-static`'s bundled `.d.ts` declares an ESM `export default`, but the package is plain CommonJS with no `"type": "module"`; under `moduleResolution: NodeNext` a normal `import ffmpegPath from "ffmpeg-static"` resolves to the whole module-namespace type instead of the string it is at runtime (`TS2352`, a known NodeNext/CJS-interop quirk, not a bug in our code). Worked around with `createRequire(import.meta.url)("ffmpeg-static")` instead of a default import, in both `narration-mux.ts` and its test file.
  - 8 new tests in `apps/daemon/src/narration-mux.test.ts` (missing-file → `INVALID_ARGS`; real-audio-file → resolves; non-audio-file → `INVALID_ARGS`; `clampOffsetMsToSeconds` unit cases; a full mux round-trip asserting the output gains an audio stream and the video-stream duration is *not* extended past the source video's ~2s even though the narration fixture is 3s; a mux-with-missing-narration-file failure case asserting the original video file is byte-for-byte/mtime untouched and no `*.narration-tmp.mp4` is left behind) plus 3 new cases appended to `session-manager.test.ts` (missing-file narration leaves session state `"recording"`; valid narration populates `manifest.narration` with the injected fake's exact args and correct `trackIndex`; a throwing fake `muxNarration` still lets `stopRecording` succeed with the base video/manifest saved and `manifest.narration` absent).

- **Phase 10 — Event Timeline** (2026-08-09): every recording now produces `<recording>.events.json` (cursor/click/best-effort-key capture) alongside the video. Built via 2 parallel subagents against the already-frozen protocol (`packages/core`'s `TimelineEvent`/`EventTimeline` schemas and the `event` notification shipped preemptively in Phase 1) — one daemon-side (TS), one macOS-sidecar-side (Swift), disjoint files, integrated cleanly with zero glue-code changes needed.
  - **Daemon** (`apps/daemon/src/event-timeline-writer.ts`, new): `EventTimelineWriter` streams incoming `TimelineEvent`s to a temp NDJSON file (`$TMPDIR/windower-<sessionId>.events.jsonl`, appends serialized through an internal write-queue so concurrent `event` notifications can't interleave) as they arrive — satisfies the contract's "streaming write, not buffered to end / crash leaves a partial, valid-JSON-lines file". `finalize(finalPath, capabilities)` drains the queue, parses the NDJSON (skipping any malformed/truncated line rather than failing), and validates the assembled result through `EventTimelineSchema.parse` before writing the final pretty-printed JSON — this is the one point that throws loudly on a genuine schema violation, per the exit criterion. `discard()` for cancel/failure paths.
  - `apps/daemon/src/session-manager.ts`: a writer + `{keystrokes: describeResult.capabilities.includes("eventTimeline.keyboard")}` is created right after `describe()` succeeds (before `startCapture`), subscribed to `handle.client.on("event", ...)`. `stopRecording` finalizes it to `eventsPathFor(outputPath)` (sibling of the video, `.events.json`, mirroring `manifestPathFor`) and populates the previously-dormant `eventTimelinePath` field on the `stop_recording` result, `OutputManifest`, and persisted `RecordingSession` (all three schemas already had this optional field since earlier phases, just never populated). Every non-finalizing exit path (`cancelRecording`, `handleCaptureEnded`, `handleSidecarExit`, the pre-`startCapture` failure branch) discards the writer so no orphaned `.events.json`/temp file survives a session that never finished.
  - **macOS sidecar** (`native/macos/Sources/WindowerSidecarCore/EventTapCapture.swift`, new): `EventTapSource`, session-scoped, two independent `CGEventTap`s (`.listenOnly` — never intercepts real input) — one for mouse+cursor (`mouseMoved`/`leftMouseDown|Up`/`rightMouseDown|Up`/`otherMouseDown|Up`), one for keyboard (`keyDown`/`keyUp`) — split specifically so a keyboard-only failure (secure-input contexts) can't take down cursor/click capture. `main.swift`'s process has no active `CFRunLoop` (blocking `readLine()` loop), so `EventTapSource.start()` spins up a dedicated background thread + run loop per session, torn down via `CFRunLoopPerformBlock`/`CFRunLoopWakeUp` in `stop()`. Cursor-move throttled to 30Hz via a pure `EventThrottle` helper (headlessly testable); coordinates converted `points × backingScaleFactor(forPoint:)` — same convention `EnumerationService.mapDisplay`/`mapWindow` already use, so timeline coordinates land in the same pixel space as `CaptureTarget.bounds`. Wired into `CaptureSessionManager`: created+started alongside `microphoneSource` in `startCapture`, stopped in `stopCapture`/`cancelCapture`/`handleStreamStoppedUnexpectedly`; a tap-creation failure never fails `startCapture` (additive-only, video capture is core).
  - **Capability-advertising tension, resolved deliberately**: `describe` is a one-shot handshake at sidecar spawn, before any session exists — no protocol-level way to report "keyboard capture worked *this* session" through it. Resolved as: advertise `eventTimeline.cursor`/`.mouse`/`.keyboard` all statically/optimistically in `main.swift`'s capability list (same granularity every other capability already has), and when the keyboard tap specifically fails to create for a session, emit the already-defined-but-previously-unused `log` notification (`{sessionId, level: "warn", message: "keyboard capture unavailable this session: ..."}`) as the actual per-session signal — documented inline in `main.swift` rather than silently picking a side.
  - 18 new Swift tests (throttle logic, pixel coordinate conversion, wire-shape encode/decode for all 5 `TimelineEvent` variants — all headless, no TCC dependency) — 100 → 118 passing. 7 new TS tests (`event-timeline-writer.test.ts` + 3 appended to `session-manager.test.ts`) exercising append→finalize round-trips through `EventTimelineSchema`, zero-event finalize, discard-on-cancel leaving no file behind, and `capabilities.keystrokes` correctly reflecting a fake sidecar's advertised capabilities via the existing `createFakeSidecarFactory`/`FakeSidecar.emitEvent` test hooks (already present from Phase 1's preemptive protocol work).
